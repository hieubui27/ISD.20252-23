# Group 23 - Design Principles Report

Use case focus: UC235 - View Product Detail

PIC: View Product Detail PIC

| Modules                                                           | PIC                     | Description                                                                                                                              | Improvement Direction                                                                      |
| ----------------------------------------------------------------- | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| ProductController                                                 | View Product Detail PIC | Handles HTTP request/response for product read and command endpoints. GET list/detail is delegated to query use cases instead of Prisma. | Keep controller thin. Do not add Prisma queries, DTO mapping, or UI formatting logic here. |
| GetProductDetailUseCase                                           | View Product Detail PIC | Coordinates validation, product lookup, not-found handling, and DTO mapping for UC235.                                                   | Keep only read orchestration here and delegate persistence/mapping to repository/mapper.   |
| GetProductsListUseCase                                            | View Product Detail PIC | Coordinates home/product list retrieval and maps records to product card DTOs.                                                           | Keep list loading separate from product command behavior.                                  |
| ProductQueryRepository interface                                  | View Product Detail PIC | Defines only query methods required by product list/detail screens.                                                                      | Keep command operations in a separate command repository if product management grows.      |
| PrismaProductRepository                                           | View Product Detail PIC | Owns Prisma queries for product list/detail data and includes type-specific relations.                                                   | Keep Prisma-specific details here and do not expose Prisma models directly to controllers. |
| ProductDetailMapper                                               | View Product Detail PIC | Converts persistence records into ProductListItemDto and ProductDetailDto.                                                               | Keep mapping logic out of use cases and controllers.                                       |
| ProductDetailDto, Product entity/type                             | View Product Detail PIC | Define common product data and type-specific response payloads.                                                                          | Keep common fields separate from Book/Newspaper/CD/DVD-specific fields.                    |
| ProductApiService                                                 | View Product Detail PIC | Centralizes Angular HTTP calls to real `/api/products` endpoints.                                                                        | Keep endpoint URLs and HTTP logic out of components.                                       |
| ProductListPageComponent, ProductCardComponent                    | View Product Detail PIC | ProductListPage owns loading/error state; ProductCard renders one product card.                                                          | Keep card presentation separate from page-level fetch state.                               |
| ProductDetailPageComponent, ProductDetailComponent                | View Product Detail PIC | ProductDetailPage owns route/fetch state; ProductDetail renders common detail fields.                                                    | Keep route and API concerns outside presentational components.                             |
| ProductSpecificInfoComponent and Book/Newspaper/CD/DVD components | View Product Detail PIC | Dispatcher selects the type component; each child renders only its own data.                                                             | Keep type-specific labels and formatting inside dedicated child components.                |
| product.model.ts                                                  | View Product Detail PIC | Defines Angular read models for list/detail and specific info types.                                                                     | Keep models free of fetching, routing, and UI state behavior.                              |

## 2. Open/Closed Principle (OCP)

| Modules                                                           | PIC                     | Description                                                                                 | Improvement Direction                                                                 |
| ----------------------------------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| ProductController                                                 | View Product Detail PIC | Closed to product-type rendering changes because it delegates detail behavior to use cases. | Add new product behavior in application/mapper layers instead of controller branches. |
| GetProductDetailUseCase, GetProductsListUseCase                   | View Product Detail PIC | Use cases stay stable while mapping/persistence details can change behind abstractions.     | Avoid adding product-type switch logic inside use cases.                              |
| ProductQueryRepository interface, PrismaProductRepository         | View Product Detail PIC | New persistence implementations can replace Prisma through NestJS DI.                       | Keep the interface stable and add new implementation classes when needed.             |
| ProductDetailMapper                                               | View Product Detail PIC | Type-specific mapping is isolated in mapper functions for Book, Newspaper, CD, and DVD.     | If more types are added, add dedicated mapper functions or a mapper registry.         |
| ProductDetailDto, Product entity/type                             | View Product Detail PIC | Common response shape can remain stable while `specificInfo` evolves per type.              | Add new specific DTOs instead of adding subtype fields to common product data.        |
| ProductApiService                                                 | View Product Detail PIC | Components stay closed to endpoint changes if the service contract remains stable.          | Keep API evolution behind service methods.                                            |
| ProductListPageComponent, ProductCardComponent                    | View Product Detail PIC | List/card views render common fields and are not changed for type-specific detail fields.   | Keep cards generic unless the product card contract changes.                          |
| ProductDetailPageComponent, ProductDetailComponent                | View Product Detail PIC | Detail page and common detail component are closed to specific type UI changes.             | Add type UI in ProductSpecificInfo children, not in page-level components.            |
| ProductSpecificInfoComponent and Book/Newspaper/CD/DVD components | View Product Detail PIC | Dedicated child components reduce changes to existing type renderers.                       | Replace dispatcher switch with a registry if product types become dynamic.            |
| product.model.ts                                                  | View Product Detail PIC | Union models allow new type-specific interfaces to be added explicitly.                     | Add a new interface and update the union when adding a supported type.                |

## 3. Liskov Substitution Principle (LSP)

| Modules                                                           | PIC                     | Description                                                                                                        | Improvement Direction                                                      |
| ----------------------------------------------------------------- | ----------------------- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| Product entity/type                                               | View Product Detail PIC | Common product contract contains only shared fields, so Book/CD/DVD/Newspaper do not fake unrelated data.          | Keep subtype-only data inside `specificInfo`.                              |
| ProductDetailDto                                                  | View Product Detail PIC | Every detail response preserves common fields regardless of product type.                                          | Ensure each new product type still returns the common DTO contract.        |
| ProductQueryRepository interface, PrismaProductRepository         | View Product Detail PIC | PrismaProductRepository can substitute any ProductQueryRepository implementation if it preserves return contracts. | Keep repository method semantics consistent across implementations.        |
| GetProductDetailUseCase, GetProductsListUseCase                   | View Product Detail PIC | Use cases can work with any repository implementation following the abstraction.                                   | Avoid relying on Prisma-only methods or hidden model behavior.             |
| ProductSpecificInfoComponent and Book/Newspaper/CD/DVD components | View Product Detail PIC | Child components follow a consistent input-only rendering contract.                                                | Keep all specific components presentational and side-effect free.          |
| ProductApiService and product.model.ts                            | View Product Detail PIC | Frontend consumes stable product contracts and does not assume one type has another type's fields.                 | Use type-specific interfaces instead of optional fields for every subtype. |

## 4. Interface Segregation Principle (ISP)

| Modules                                                                                                      | PIC                     | Description                                                                                    | Improvement Direction                                                          |
| ------------------------------------------------------------------------------------------------------------ | ----------------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| ProductQueryRepository interface                                                                             | View Product Detail PIC | UC235 depends only on `findProducts` and `findProductById`.                                    | Keep create/update/delete/stock operations out of this interface.              |
| GetProductDetailUseCase, GetProductsListUseCase                                                              | View Product Detail PIC | Each use case depends only on query methods it needs.                                          | Split future product commands into separate use cases and interfaces.          |
| ProductController                                                                                            | View Product Detail PIC | GET endpoints depend on query use cases; command endpoints remain delegated to ProductService. | Avoid making one service interface serve every product workflow.               |
| ProductDetailDto, ProductListItemDto                                                                         | View Product Detail PIC | List and detail responses are separated so list screens do not depend on full detail payloads. | Keep response DTOs focused by screen/use case.                                 |
| ProductApiService                                                                                            | View Product Detail PIC | Exposes only read methods used by list/detail product screens.                                 | Add new methods only when a component needs that read operation.               |
| ProductListPageComponent, ProductCardComponent                                                               | View Product Detail PIC | ProductCard receives ProductListItem only, not full ProductDetail.                             | Keep card inputs minimal.                                                      |
| ProductDetailPageComponent, ProductDetailComponent                                                           | View Product Detail PIC | ProductDetail receives ProductDetail only; route state remains in the page.                    | Keep page and detail component input contracts separate.                       |
| BookSpecificInfoComponent, NewspaperSpecificInfoComponent, CDSpecificInfoComponent, DVDSpecificInfoComponent | View Product Detail PIC | Each child receives only the specific info it displays.                                        | Do not pass full ProductDetail into specific child components.                 |
| product.model.ts                                                                                             | View Product Detail PIC | Models are split into common list/detail and specific info interfaces.                         | Avoid a single oversized product interface with mostly unused optional fields. |

## 5. Dependency Inversion Principle (DIP)

| Modules                                                                           | PIC                     | Description                                                                                     | Improvement Direction                                                 |
| --------------------------------------------------------------------------------- | ----------------------- | ----------------------------------------------------------------------------------------------- | --------------------------------------------------------------------- |
| ProductController                                                                 | View Product Detail PIC | Depends on injected use cases/services rather than manually creating classes or calling Prisma. | Keep DI as the only construction path for product dependencies.       |
| GetProductDetailUseCase, GetProductsListUseCase                                   | View Product Detail PIC | Depend on ProductQueryRepository abstraction via PRODUCT_QUERY_REPOSITORY token.                | Do not inject PrismaService into use cases.                           |
| ProductQueryRepository interface, PrismaProductRepository                         | View Product Detail PIC | Infrastructure implements domain/application abstraction and is bound in ProductModule.         | Keep NestJS provider binding in module configuration.                 |
| ProductModule                                                                     | View Product Detail PIC | Binds PRODUCT_QUERY_REPOSITORY to PrismaProductRepository using NestJS DI.                      | Swap implementations by changing provider binding, not use case code. |
| ProductDetailMapper, ProductDetailDto, Product entity/type                        | View Product Detail PIC | Mapping and DTO layers are independent of controllers and PrismaService.                        | Keep DTOs as plain contracts without infrastructure dependencies.     |
| ProductApiService                                                                 | View Product Detail PIC | Angular components depend on ProductApiService instead of direct HttpClient calls.              | Keep HTTP concerns centralized in core services.                      |
| ProductListPageComponent, ProductDetailPageComponent                              | View Product Detail PIC | Pages receive data through injected ProductApiService.                                          | Avoid hardcoded fetch calls in multiple components.                   |
| ProductDetailComponent, ProductSpecificInfoComponent and type-specific components | View Product Detail PIC | Presentational components depend on input data, not API services.                               | Keep them reusable by avoiding service injection unless truly needed. |
| product.model.ts                                                                  | View Product Detail PIC | Models are independent of Angular HttpClient and backend implementation classes.                | Keep shared contracts plain and framework-light.                      |
